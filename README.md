# FraudShield-RT — Real-Time Fraud Detection, Optimised for Financial Cost

> ⚠️ **Illustrative results on synthetic data.** All metrics below come from
> realistic synthetic transactions generated by this repo (seed 42, fraud
> rate 0.88%). They demonstrate the pipeline end-to-end; they are **not**
> real-world performance claims. See [Methodology](#methodology) and
> [Limitations](#limitations).

## Resumen en español

FraudShield-RT es un pipeline de detección de fraude para pagos con tarjeta
/ transferencias, pensado para el problema real: **menos del 1% de las
transacciones son fraude**, así que la métrica que importa no es la exactitud
sino el costo en pesos.

- **Variables de velocidad** (10 min, 1 h, 24 h por cuenta, dispositivo y
  comercio) calculadas **solo con el pasado** — sin fuga temporal.
- **Modelo LightGBM** (con fallback a XGBoost / HistGradientBoosting),
  entrenado con **división fuera de tiempo** (60/10/30) y **calibración
  isotónica**, optimizado para **PR-AUC**, no solo ROC-AUC.
- **Umbral por costo**: se elige el umbral que minimiza el costo total
  (fraude no detectado + revisión manual + fricción por falsos rechazos),
  no el arbitrario 0.50.
- **API FastAPI** (`POST /score`) que devuelve el puntaje y los **3 motivos
  principales** en milisegundos, y un **simulador de ahorro neto** frente a
  reglas estáticas.
- **Resultados (sintéticos, ilustrativos)**: PR-AUC **0.573** (azar: 0.008),
  ROC-AUC 0.906, KS 0.696; en el test, el modelo cuesta **$241,710 MXN**
  frente a $285,865 de la mejor regla estática (**ahorro $44,154**) y
  $726,700 sin controles (**ahorro $484,989**).

## Results (synthetic data — illustrative)

Dataset: 60,295 synthetic transactions, 1 Jan – 1 Mar 2026, fraud rate
**0.88%** (530 fraud). Test set (last 30% of time): 18,089 transactions,
151 fraud, fraud volume $726,700 MXN. Full numbers in
[`outputs/metrics.json`](outputs/metrics.json) and
[`outputs/savings_simulation.json`](outputs/savings_simulation.json).

| Metric | Value |
|---|---|
| **PR-AUC (test)** | **0.573** (random baseline: 0.008 — ~69×) |
| ROC-AUC (test) | 0.906 |
| KS statistic (test) | 0.696 |
| Optimal threshold (chosen on calibration split) | **0.02** |
| Test cost @ optimal threshold | **$241,710 MXN** (P 0.29, R 0.63, 95/151 fraud caught) |
| Test cost @ threshold 0.50 | $419,370 MXN (P 0.96, R 0.47) |
| Best static rule (amount > $5,000 or ≥5 txns/h) | $285,865 MXN |
| **Net saving vs. best static rule** | **$44,154 MXN** on the test set |
| Net saving vs. amount > $5,000 rule | $61,709 MXN |
| Net saving vs. amount > $2,000 rule | $126,014 MXN |
| Net saving vs. no controls (approve all) | $484,989 MXN |

**Why is the optimal threshold 0.02, not 0.50?** Two honest reasons, both
worth stating in an interview: (1) calibrated probabilities are low
because the base rate is 0.83% — a score of 0.02 is already ~2.4× the base
rate; (2) the cost matrix is asymmetric — missing one ~$4,800 fraud costs
as much as ~40 false alarms at $120 each. A 0.50 threshold "looks" clean
and loses $177,660 more on this test set. The threshold is chosen on the
*calibration* split, never on the test split.

Top features by LightGBM importance: `device_age_days`,
`account_age_days`, `time_since_last_acct_min`, `hour_sin`,
`acct_avg_amt_24h` — i.e. new devices/accounts, burst timing and
amount-vs-usual dominate, which matches how card fraud actually behaves.

## Methodology

1. **No temporal leakage, by construction.** Velocity features are computed
   with `np.searchsorted` over strictly earlier timestamps
   (`side="left"` on the current timestamp). `tests/test_features.py`
   asserts the first transaction of an account has zero velocity, window
   amounts exclude the current row, and future rows never leak backwards.
2. **Out-of-time split, not random.** Train = first 60% of time,
   calibration = next 10%, test = last 30%. A random split would let the
   model memorise accounts/devices and inflate metrics.
3. **PR-AUC as the headline metric.** With <1% fraud, ROC-AUC is
   flattering (most negatives are trivially easy). Precision-Recall AUC
   measures what operations cares about: of the alerts raised, how many
   are fraud, and how much fraud is caught.
4. **Isotonic calibration** on the calibration split (implemented in
   `src/calibrated_model.py` — sklearn ≥ 1.6 removed
   `CalibratedClassifierCV(cv="prefit")`). A calibrated score can be
   compared to a cost-derived threshold; an uncalibrated one cannot.
5. **Cost-based threshold.** Cost matrix (MXN, documented assumptions —
   re-estimate with the business): FN = full transaction amount,
   FP = $120 (review + customer friction), TP = $60 (manual review),
   TN = $0. See `src/cost_optimization.py`.
6. **Explainability.** `src/explain.py` gives the top-3 human-readable
   reasons per case (importance-weighted deviation, <1 ms — what the API
   uses) and a best-effort SHAP path (`shap.TreeExplainer`) for offline
   review when SHAP is installed.

## How to run

```bash
# 1. Install (Python >= 3.10)
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 2. Everything, end to end (data -> train -> savings -> latency -> tests)
bash run_all.sh
# ... or step by step:
python -m src.generate_synthetic --n 60000 --out data/synthetic_transactions.csv
python -m src.train                        # writes models/model.pkl, outputs/metrics.json
python scripts/simulate_savings.py         # writes outputs/savings_simulation.json
python scripts/latency_test.py --n 500
pytest -q                                  # 8 tests

# 3. API
uvicorn src.api.main:app --host 0.0.0.0 --port 8000
curl http://127.0.0.1:8000/health
# Docs: http://127.0.0.1:8000/docs
```

`make run-all` does the same via the Makefile. A `Dockerfile` is included
(`docker build -t fraudshield-rt . && docker run -p 8000:8000 fraudshield-rt`).

### Using real data

The project runs with **zero downloads** (synthetic data). To use
IEEE-CIS Fraud Detection or PaySim instead, see
[`docs/real_data.md`](docs/real_data.md) for the column mapping, then:

```bash
python -m src.train --data data/ieee_train.csv
```

## Limitations

- **Synthetic data.** Fraud patterns here (night + new device + bursts)
  are realistic but simplified; a real portfolio has device fingerprints,
  merchant risk, 3-D Secure outcomes, chargeback labels with delay, and
  concept drift. Treat every number as illustrative.
- **Cost assumptions.** FP = $120 / TP = $60 are documented guesses, not
  a business's measured costs. Change them in `src/cost_optimization.py`
  and the optimal threshold moves — that sensitivity is the point.
- **Velocity features in the API are caller-provided.** In production a
  feature store / stream processor (e.g. Flink, Redis) owns the sliding
  windows; the API accepts them pre-computed so scoring stays in ms.
  `src/features.py` is the batch reference implementation of the same logic.
- **Calibration set is small** (6,029 rows, 46 fraud) — isotonic steps are
  coarse, which is part of why the optimal threshold is low. With real
  volume, use a larger calibration window and monitor calibration drift.
- **No drift monitoring in this repo** (PSI / label-delay handling are
  covered in the companion project CreditRisk-IFRS9).
